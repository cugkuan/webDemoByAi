## 📊 测试场景详解

### demo.sh 中的测试

#### 阶段 1-7：功能验证
```
1. 创建任务
   ↓
2. 首次查询（DB 查询）
   ↓
3. 立即重复查询（L1 缓存命中）
   ↓
4. 查询单个任务（DB 查询 + 缓存写入）
   ↓
5. 立即重复查询（L1 缓存命中）
   ↓
6. 更新任务（清除缓存）
   ↓
7. 查询已更新的任务（DB 重新查询）
```

**预期结果**：
- 步骤 3、5 应比 2、4 快 10-100 倍
- 步骤 7 应与步骤 2 耗时接近

#### 测试 1：无缓存状态
```
清除所有缓存 → 100 个并发请求 → 每次都查 DB
```

**指标**：
- QPS: 500-1000（取决于 DB 性能）
- 每个 goroutine 处理时间: 10-50ms

#### 测试 2：L1 缓存命中
```
1000 个并发请求 → 所有 hit L1 缓存
```

**指标**：
- QPS: 10,000+ （本地内存超快）
- 每个 goroutine 处理时间: < 1ms

#### 测试 3：混合读写
```
500 个读请求 + 修改操作 → 缓存清除 → 重新查 DB
```

**指标**：
- 测试缓存失效机制
- 写操作不应阻塞读操作

#### 测试 4：极限并发
```
5000 个并发请求一次性发出 → 测试 goroutine 上限
```

**指标**：
- 所有请求应在 30 秒内完成
- 没有超时错误
- goroutine 数量回落到正常水平

### load_test.sh 中的测试

## 🐛 常见问题

### Q: 为什么 QPS 这么低？

**可能原因**：
1. Redis 未启动 → 仅用 L1 缓存
2. 数据库连接过慢
3. 网络延迟
4. CPU 限制

**解决**：
- 启动 Redis: `redis-server &`
- 检查数据库连接: `mysql -u root -p`
- 使用本地网络测试

### Q: 测试中断或超时

**可能原因**：
1. 内存不足
2. 文件描述符耗尽
3. 网络问题

**解决**：
- 减少并发数: 从 200 → 100
- 减少请求数: 从 10000 → 5000
- 检查系统资源: `top` / `lsof`

### Q: 如何持续监控性能？

```bash
# 循环运行测试
while true; do
    bash load_test.sh
    sleep 60  # 等待 60 秒后再次测试
done
```

## 📚 进阶用法

### 自定义压力测试

创建 `custom_test.sh`：

```bash
#!/bin/bash
BASE_URL="http://localhost:8080"

# 测试特定端点
for endpoint in "/api/tasks" "/api/tasks/1" "/api/tasks/2"; do
    echo "Testing: $endpoint"
    
    start=$(date +%s%N)
    for ((i=1; i<=1000; i++)); do
        curl -s "$BASE_URL$endpoint" > /dev/null 2>&1 &
    done
    wait
    end=$(date +%s%N)
    
    duration=$(((end - start) / 1000000))
    qps=$((1000 * 1000 / duration))
    echo "QPS: $qps"
    echo ""
done
```

### 使用 Apache Bench（如果安装）

```bash
ab -n 10000 -c 100 http://localhost:8080/api/tasks
```

- 最小/最大响应时间
